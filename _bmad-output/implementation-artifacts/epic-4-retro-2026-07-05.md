## What Went Well

### 1. Pre-implementation Discovery (Story 4.2)
The entire scheduler member fan-out was pre-built during Epic 2 (Stories 2.2–2.5). Story 4.2 became a verification-only story — no production code written. Instead of blindly reimplementing, the story explicitly verified each AC against the existing code and added a missing keyboard assertion test. This is a mature pattern: check before building.

### 2. Code Review Caught a Real P1 Crash
Story 4.1 code review found a `TypeError` crash in `receive_remove_select`: the inner `conn.execute(...).fetchone()` returned `None` when a member was deleted between list display and selection, causing a crash that would be silently swallowed. The code review also flagged a violation of AD-1 (inline SQL bypassing `member_repo`). Both were patched before reaching users.

### 3. Pattern Reuse — `repairman_handlers.py` as Template
Story 4.1's ConversationHandler followed `repairman_handlers.py` almost exactly: admin-only auth, `context.user_data` state, HTML output with `html.escape()`, text-based confirmation ("Có"/"Không"), `member_repo` for all DB access. Fast, consistent, no architecture surprises.

### 4. Architecture Held Across Both Stories
AD-1 (bot → db one-way dependency), AD-5 (scheduler uses its own DB connection), AD-7 (conversation state in `context.user_data` only) — all respected without effort. The `get_all_members()` function designed in Epic 2 served all four scheduler fan-out loops unchanged.

### 5. Test Quality
+33 tests, 0.35s full suite execution, 0 failures. Story 4.2 added a `reply_markup is None` assertion even as a verify-only story — proactive coverage improvement.

## Challenges & Growth Areas

### 1. Unicode `isdigit()` Bug — Partial Fix
The `text.isdigit()` → `int(text)` pattern fails for Unicode digit characters (e.g., `"²"` passes `isdigit()` but raises `ValueError` on `int()`). Patched in `member_handlers.py` (Story 4.1) but the same pattern lives in `repairman_handlers.py` and potentially `incident_handlers.py`. We fixed the symptom in one place and deferred the pattern.

### 2. Systemic Deferred Debt Accumulating
`effective_message None guard missing`, `user_data keys not cleared on END`, `ADMIN_USER_ID=0 silent fallback` — these appear across Stories 3.1, 4.1, and earlier, each time labeled "pre-existing systemic pattern" and deferred. `deferred-work.md` now has 10 sections. This is an intentional trade-off for a personal household bot, but the pile deserves a periodic review.

### 3. No Prior Retrospectives
This is the first retrospective for the project. Epic 4 is the 4th epic and 13th story. We have no baseline data: no prior action items to check, no velocity trends, no process continuity. Starting the habit now is the right call, but context is missing.

### 4. AC-5 Log Level Not Asserted
All four scheduler test files verify that member delivery iteration continues after a failure (`*_continues_on_member_failure` tests) but none assert that `logger.warning` was actually called. A future refactor that silently swallows exceptions would pass all tests.

## Key Insights

1. **Verify before building.** Story 4.2's pattern — check whether implementation already exists before writing code — saved significant time. This should be an explicit first step in any story that builds on scheduler or DB infrastructure.

2. **Code review finds real bugs.** The P1 crash in `receive_remove_select` was not caught by tests (the TOCTOU scenario requires a member to be deleted between two handler calls). Code review is the only layer that would catch this class of bug. The review phase is doing its job.

3. **Pattern fixing should be global.** When a bug is found by analogy (Unicode `isdigit()`), the fix should sweep all similar call sites, not just the current story's files. A partial fix leaves known bugs deferred indefinitely.

4. **Retrospectives create continuity.** Without a prior retro, we can't know if this epic was better or worse than Epic 3. Starting now establishes the baseline.
